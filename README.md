# VictorySearcher

Внутренний инструмент для HR-отдела и аналитиков коммерции, который автоматизирует две рутинные задачи: отбор резюме и сбор данных о рынке труда.

## О проекте

Рекрутёры тратят часы на ручной просмотр сотен резюме, а аналитики — на сбор зарплат и требований по вакансиям из разных источников. VictorySearcher закрывает обе боли:

- **Скоринг резюме** — рекрутёр создаёт вакансию и загружает резюме, система ранжирует кандидатов по релевантности с помощью LLM и выдаёт отсортированный список с оценками и обоснованием на русском языке.
- **Аналитика рынка труда** — автономный сбор вакансий по заданным ролям из нескольких источников по расписанию. Показывает зарплатные вилки, динамику, востребованные навыки и активность рынка.

## Сервисы

Проект состоит из трёх частей. Подробности по каждой — в её локальной документации.

| Сервис | Роль в проекте | Документация |
|--------|----------------|--------------|
| **VictorySearcher.Service** | Бэкенд: скоринг резюме через LLM, фоновый сбор аналитики, REST API. | [README](VictorySearcher.Service/README.md) |
| **VictorySearcher.Web** | Веб-интерфейс: создание вакансий, загрузка резюме, просмотр результатов и аналитики. | [README](VictorySearcher.Web/README.md) |
| **VictorySearcher.Design** | Дизайн-мастерская: проработка макетов фронтенда вместе с Claude — спецификации (токены, типографика, компоненты, экраны), HTML/CSS-прототипы и референсы. Не разворачивается, служит источником истины для UI. | [design/](VictorySearcher.Design/design/) |

## Технологический стек

- **Бэкенд**: C# / .NET 9
- **Фронтенд**: React + TypeScript (Vite)
- **Деплой**: Docker Compose

## Как я работаю с Claude

Проект собран под управлением ИИ-агентов, но решение всегда остаётся за мной: задача идёт через цепочку специализированных агентов, и каждый шаг я утверждаю вручную.

**Жизненный цикл одной задачи:**

1. Ставлю задачу агенту **`architecture-designer`** — он прорабатывает план решения (для любого сервиса) с обоснованием, альтернативами и самокритикой.
2. Читаю план. Если устраивает — передаю ссылку на него агенту конкретного сервиса (для бэкенда — **`dotnet-senior`**).
3. Сервисный агент сверяется с планом, подтверждает и начинает реализацию.
4. Я просматриваю и **утверждаю каждое изменение** — агент ничего не пишет в обход ревью.

**Из чего собран процесс** (всё лежит в `.claude/`):

| Механизм | Что это | Как подключается |
|----------|---------|------------------|
| **Агенты** | `architecture-designer` (план и архитектура), `dotnet-senior` (бэкенд), `documentation-specialist` (документация) | Запускаются под конкретную задачу; у каждого своя дисциплина — confidence и рефлексия у архитектора, запрет на выдумки у документатора |
| **Скиллы** | `git-commit`, `write-claude-md` | Подгружаются по требованию, когда задача попадает в их триггер — не висят в контексте постоянно |
| **Правила** | `progress-json`, `task-md`, `ai-collaboration`, `domain-entity-changes` | Применяются автоматически при наступлении условия (правка `TASK.md`, изменение доменной сущности и т.д.) |
| **CLAUDE.md** | Корневой реестр + по одному на сервис | Загружается в каждую сессию; корневой держит общий список скиллов и правил, потому что из подпапки сервиса они не подхватываются сами |
| **Память агентов** | `.claude/agent-memory/<agent>/` | Переживает сессии: профиль, принятые решения, обратная связь |

Из подпапки сервиса корневые `.claude/` и `docs/` не видны автоматически, поэтому в каждом сервисе лежит `settings.json`, открывающий их на чтение, а CLAUDE.md сервиса начинается с обязательного «сначала прочитай корневой CLAUDE.md».

**Артефакты этой работы:**

- **`CLAUDE.md`** — правила проекта для агентов, эволюционировавшие по git-истории, а не написанные задним числом.
- **[`docs/ai-collaboration.md`](docs/ai-collaboration.md)** — ключевые эпизоды и решения, которые я отверг (с причинами): где модель ошиблась и что сделано вместо.
- **`progress.json`** в каждом сервисе — журнал реализованного, обновляется после каждого заметного изменения.

## Как запустить

```bash
git clone <repo-url>
cd VictorySearcher
cp .env.example .env   # заполнить ключи LLM и учётные данные
docker compose up -d --build
```

Поднимаются три контейнера в одной сети (`victory-net`): фронтенд, бэкенд и PostgreSQL.

| Контейнер | Что это | Адрес |
|-----------|---------|-------|
| `web` | Веб-интерфейс (Vite preview на Node), проксирует `/api` на бэкенд | `http://localhost:3000` |
| `api` | Бэкенд .NET, миграции и сидинг выполняются при старте | `http://localhost:5000` |
| `db`  | PostgreSQL 16, данные в томе `postgres_data` | `localhost:5432` |

Точка входа — **`http://localhost:3000`** (хост-порт `3000` выбран, чтобы не конфликтовать с локальным `vite dev` на `5173`). Обращаться к бэкенду напрямую не нужно: фронтенд проксирует запросы `/api` внутри сети по имени сервиса `api`.

### Переменные окружения

Подстановка значений в `docker-compose.yml` берётся из корневого `.env` (см. `.env.example`); если переменная не задана — действует значение по умолчанию. Для реального скоринга обязателен `LLM_API_KEY`. Бэкенд внутри контейнера получает конфигурацию через переменные окружения (секция `environment` в compose), `.env` внутрь образа не копируется.
