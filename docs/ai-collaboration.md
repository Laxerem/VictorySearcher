# История работы с ИИ

Выжимка ключевых эпизодов совместной работы с Claude: контекст этапа и решения, которые были отвергнуты — с причинами. Не сырой лог, а разбор того, где модель ошиблась и что сделано вместо.

## Эпизоды

### Продумывание архитектуры (Backend)

**Контекст:** Выбор общей структуры бэкенда под две фичи — скоринг резюме и аналитику рынка. Решали, какой паттерн положить в основу и как организовать Application-слой, чтобы код оставался поддерживаемым другими инженерами команды. Остановились на Clean Architecture (монолит, .NET 9).

#### Отказ от решений

1. Claude предлагал MediatR (Command/Handler CQRS) для Application-слоя — отвергнуто, потому что обработчиков немного (два главных сервиса: скоринг и аналитика), и MediatR добавляет накладные расходы без реальной пользы в этом масштабе.

### Авторизация

**Контекст:** Реализация JWT-авторизации для единственного системного пользователя — без регистрации, учётные данные берутся из конфигурации. Успешный логин возвращает Bearer-токен для заголовка `Authorization`. Параллельно, как рефлексия над допущенными в этом эпизоде ошибками, был заведён агент `dotnet-senior`.

#### Отказ от решений

1. Claude поместил генерацию JWT-токена внутрь `AuthService` — отвергнуто, потому что это нарушает SRP: проверка учётных данных и генерация токена — разные ответственности. Генерация вынесена в отдельный `JwtProvider`.
2. Claude вернул `string?` из `IAuthService.LoginAsync` вместо `Result<string>` — отвергнуто, потому что в проекте принят `Result<T>` для ожидаемых ошибок сервисного слоя, это прямо прописано в CLAUDE.md.
3. Claude использовал анонимный тип `new { token }` и `IActionResult` в контроллере — отвергнуто, потому что контракты API должны быть типизированными `record`-типами в папке `Contracts/`, а контроллер всегда возвращает `ActionResult<TResponse>`.

### Разработка скоринга резюме

**Контекст:** Первая версия скоринга: загрузка резюме, парсинг текста, отправка в LLM и сохранение результатов. По ходу потребовался рефакторинг для устранения жёсткой связанности и нарушений SRP, допущенных в первоначальной реализации.

#### Отказ от решений

1. Claude создавал `OpenAIClient` прямо внутри метода `ResumeAnalyserService.AnalyseAsync` — отвергнуто, потому что это нарушает SRP (сервис не должен управлять жизненным циклом HTTP-клиента) и делает код жёстко связным: подменить LLM-провайдер через DI невозможно. Создание клиента вынесено в отдельную реализацию `IAnalyserLlmClient`.

### Управление резюме и инкрементный скоринг

**Контекст:** Расширение сервиса: пагинированный список загруженных резюме с флагом проверки, просмотр содержания и скачивание файла, счётчики проверенных/непроверенных, инкрементный скоринг (повторный запуск обрабатывает только непроверенные резюме). По ходу всплыл баг: результаты скоринга возвращались только из последнего запроса, и при инкрементном режиме оценки прошлых запусков пропадали из ответа — чинили дедупликацией до последнего результата на каждое резюме по всей вакансии.

#### Отказ от решений

1. Claude объявил поле `Format` в `ResumeListItemDto` типом `string` — отвергнуто, потому что в доменном слое уже существует enum `FileFormat`, и замена его на `string` в DTO означает потерю типизации без причины.
2. Claude поместил маппинг MIME-типов (`FileFormat` → `"application/pdf"` и т.д.) в `ResumeService` и передавал готовый `MimeType: string` в `ResumeFileDto` — отвергнуто, потому что MIME-тип — деталь HTTP-транспорта и не относится к бизнес-логике. `ResumeFileDto` хранит `FileFormat`, маппинг выполняется в контроллере.
3. Claude реализовал `GetContentAsync` через прямое чтение файла (`File.ReadAllTextAsync`) — отвергнуто, потому что логика парсинга резюме по формату уже инкапсулирована в `ResumeParserDispatcher`. Дублировать её в сервисе — нарушение DRY и игнорирование существующей абстракции.
4. Для устранения бага с неполным списком результатов Claude предложил дедупликацию через загрузку всех результатов из БД с последующим `GroupBy` в памяти — отвергнуто, потому что при тысячах резюме это неприемлемо по памяти и производительности. Реализовано через коррелированный подзапрос `NOT EXISTS`, выполняемый целиком на стороне PostgreSQL.
